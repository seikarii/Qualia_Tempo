 Contenedor IoC Automático (InversifyJS) vs Instancia Manual
Frontend (Actualizado): inversify.config.ts implementa un contenedor IoC centralizado con bindings declarativos para todos los servicios, siguiendo el patrón de Composition Root automático.
Backend (Desactualizado): CompositionRoot.py instancia servicios manualmente en métodos como _initialize_particle_system(), violando el principio de IoC automática.
Impacto: El backend carece de inversión de control verdadera, haciendo el código más rígido y difícil de testear.
2. ApplicationCompositionRoot para Bootstrap Encapsulado
Frontend (Actualizado): ApplicationCompositionRoot.ts encapsula toda la lógica de bootstrap sin exponer el contenedor IoC, proporcionando una API limpia para la inicialización de la aplicación.
Backend (Desactualizado): No existe equivalente; el bootstrap se maneja directamente en rutas o scripts principales.
Impacto: Falta abstracción para el ciclo de vida de la aplicación, exponiendo detalles de implementación al código cliente.
3. Event Contracts Centralizados
Frontend (Actualizado): events.contracts.ts sirve como fuente única de verdad para todas las estructuras de datos de eventos, eliminando dependencias circulares.
Backend (Desactualizado): No hay archivo equivalente; los contratos de eventos están dispersos o inexistentes.
Impacto: Mayor riesgo de inconsistencias en la comunicación event-driven entre servicios backend.
4. Decoradores Avanzados para Arquitectura Event-Driven
Frontend (Actualizado): Decoradores como @OnEvent, @AdaptAndEmit, @BrowserOnly automatizan suscripciones, adaptación de protocolos y abstracción de plataforma.
Backend (Desactualizado): Solo decoradores básicos (@log_execution, @handle_errors); faltan decoradores para event handling automático.
Impacto: El backend requiere código boilerplate manual para manejo de eventos, violando el principio de automatización.
5. Testing con Isolated Containers
Frontend (Actualizado): test-container-factory.ts crea un contenedor completamente nuevo por test, garantizando aislamiento total.
Backend (Desactualizado): test_composition_root.py es menos sofisticado, sin énfasis en aislamiento por contenedor.
Impacto: Riesgo de contaminación entre tests en backend, afectando la fiabilidad de las pruebas.
6. Direct Configuration Injection Pattern
Frontend (Actualizado): Configuraciones inyectadas directamente como objetos tipados (ej: MyServiceConfig), no vía un servicio de configuración genérico.
Backend (Desactualizado): Configuración menos estructurada, sin patrón consistente de inyección directa.
Impacto: Acoplamiento al servicio de configuración, violando el principio de dependencias explícitas.
7. Config Manifest Externalizado
Frontend (Actualizado): ConfigManifest en inversify.config.ts mapea servicios a archivos YAML externos para configuración.
Backend (Desactualizado): Configuración hardcodeada o menos externalizada.
Impacto: Falta flexibilidad para adaptar comportamiento sin cambios de código.
8. Interfaces Estrictas para Todos los Servicios
Frontend (Actualizado): Cada servicio tiene una interfaz dedicada (ej: IQualiaStateCalculatorService), inyectada en constructores.
Backend (Desactualizado): Interfaces menos consistentes o ausentes.
Impacto: Menor type safety y mayor acoplamiento en backend.
9. Arquitectura de Decoradores Más Rica
Frontend (Actualizado): Decoradores transversales avanzados para logging, validación, throttling, etc.
Backend (Desactualizado): Decoradores limitados a logging y error handling básico.
Impacto: Falta automatización de concerns transversales como validación de eventos o throttling.
10. Patrón de Configuración Tipada con Contratos Dedicados
Frontend (Actualizado): Contratos específicos para configuración (ej: IQualiaCalculatorConfig.contracts.ts) con validación.
Backend (Desactualizado): Configuración menos tipada y validada.
Impacto: Mayor riesgo de errores de configuración en runtime.
